# 把课程变成能跟着阅读变化的教材：实际复现与判断

日期：2026 年 10 月 10 日。本轮从北京时间 16:43:51 开始，至 18:44:09 完成，实际持续 2 小时 0 分 18 秒。持续测试和版本指纹见同目录 `RESULTS.json`；设计先于实现冻结。全文中的“通过”只指相应检查，不等于学习效果或用户认可。

## 我的判断

**值得继续做，已经能做出实用的 HTML 原型。眼下最值得做的是一章能认真读的教材，而不是一个自动生成所有课程动画的大平台。**

你的核心想法是让读者自己决定解释的速度。读到“把这一维拆成两个头”，图就停在拆开的状态；回头读上一段，图也能回去。这种形式适合张量的形状、算法的中间状态、概率如何一起变化。它比固定播放速度的视频更容易回读，也能比单独一张最终结果图提供更多过程信息。

但“文字加视觉输入会提高学习效率”目前只能算需要检验的假设。更多输入也可能变成更多干扰。特别是鼠标被当作阅读指令之后，原来无意识的习惯可能变成一件需要操心的事。

文字和图都主要通过眼睛进入。图的好处，是把句子里难追踪的关系直接摆出来，让你少在脑中拼接；普通教材也可以有很好的图表。这个方案强化了这种表达和自主阅读的节奏，没有恢复老师的声音，也不能把“感官种类更多”当作收益证明。

连续动画也有适合的地方，例如观察梯度下降的轨迹、训练过程的趋势，或本身随时间变化的机制。对本轮拆轴、共享分母这类例子，先让读者停住看清状态更合适；是否增加短暂过渡，可以另做比较。

我建议把光标跟随保留下来，作为你这类阅读习惯的默认选项，同时保留阅读位置、完整静态图、暂停和纯文字。不要把它当成所有读者必须使用的唯一入口。也不要把光标位置叫作眼睛位置：我们知道鼠标在哪，不知道你看到了哪，更不知道你理解了哪。

对于旧 concept2motion，我建议**保留研究材料和少量可靠方法，新阅读框架独立发展**。没有必要先把旧作者、裁判、视频导出和反馈循环全部重构一遍，才开始验证这个产品。旧项目值得借鉴的是可复现的检查方法；这次产品的关键则是教材正确、段落对应明确、回读自然。

### Video2Book 的实际限制

它不只是一个 Markdown 转 HTML 脚本。真正费力的部分是听音、拿到逐字稿、按来源写长文，再整编成教材。本轮下载了真实 P02 音频并生成任务计划，但没有它要求的原生 `read_audio`／`read_media` 听音通道，也没有设置 Bilibili 字幕所需的 SESSDATA。

上游 [Video2Book 技能](/home/yang-zhi/文档/ChatGPT/concept2motion/work/reading-textbook/upstreams/video2book/skills/video2book/SKILL.md) 明确要求：“字幕缺失时没有听音通道就停下提示挂载”。因此我没有装一个本地识别模型冒充规定的听音流程，更没有靠已有教材反推逐字稿。P02 的新写作停在这里，是本轮完整复现缺口。

为验证已有教材后面的整编部分，我从第一册按真实原始区间取出三篇章节，记录文件哈希与切片位置，再调用原 `cluster-articles` CLI。它确实得到一册约 153.9 KB 的三章教材。**这是既有文字重新整编，不是新模型从视频生成教材。** 包含全部 35 集的原任务拓扑有 37 块；严格检查输出的 37 个 `no_article` 是这份全拓扑计划缺文章，不能把它解释为本轮尝试了 37 次新生成。

本轮讲解由当前已登录 Codex 会话编写。额外的独立作者／裁判模型请求为 0，没有提取登录令牌或使用额外付费服务。这个原型能证明框架可以承载经过核对的教材，尚未测出自动批量编写图解的成功率、费用或耗时。

## 真正做出来的阅读方式

页面是一条从上往下的正文。图放在对应小节里，在这个小节的阅读期间留在附近；没有左右分栏，没有逐页点击，也没有启动后一直播放的动画。

你说鼠标通常跟着当前段落移动、时常停一下，所以默认按段落绑定。进入一段并停留约 170 毫秒后，图切到这一段的明确状态。这个数值是原型的可调选择，尚未证明最适合你或其他人。

| 情况 | 当前行为 |
|---|---|
| 正常跟读、停一下 | 显示这一段对应的图 |
| 快速划过或在相邻段来回晃 | 不急着换图；回到当前段会取消邻段的候选切换 |
| 回读前文 | 可以回到先前状态，不依赖已经播放过什么 |
| 选字、复制 | 冻结切换，避免一边选字一边变图 |
| 鼠标不动，只滚动页面 | 取消旧候选，不把页面从鼠标下面经过误当成新的跟读 |
| 手机／触屏 | 使用正文的阅读位置触发；同样有短暂停留判断 |
| 键盘 | Tab 聚焦解释段落，可正向和反向阅读 |
| 不想自动跟随 | 可暂停；完整静态模式在每段显示对应图；也可只读文字 |
| 脚本、数据或 WASM 出错 | 保留能读的正文和静态图；不可用的控制不会假装正常 |
| 打印 | 输出完整的静态状态图和正文 |

Zanim 的时间值在这里被当作明确状态的地址：例如 0 是未拆轴，1 是拆轴，2 是换轴，3 是强调存储。读者可以按 0→3→1→2 的顺序跳，画面仍能定位到同一状态。本轮默认直接停到目标状态，没加入逐帧播放的短过渡；以后可以另测短过渡是否有助追踪对象，不能预先认定越流畅越好。

图里同一个元素尽量保持同一编号和颜色。文字应解释“什么变了、什么没变”，而不是只说“如图所示”。这比加炫酷运动更有用。

小屏幕的代价也真实存在：图占掉一部分阅读高度。这一版放大了数字，把 24 个存储位置拆成两行；但对更复杂、需要许多标签的图，不能只缩小整张桌面图就算支持手机。后续必须考虑简化图、展开细节或降低固定占用。

## 三个例子分别验证了什么

### 张量：分组变了，不代表内存搬家

从 24 个编号开始，先排成 `[3,8]`，再拆成 `[3,2,4]`，最后交换 batch 和 head，变成 `[2,3,4]`。编号 9 一直是同一个元素；它从第二份输入的第一个特征，变成第一组 head 下第二份输入的第一个特征。上面的图重新分组，下面的地址顺序保持不动。

这个例子还抓出了已有教材的一处重要问题：原文把 `rearrange` 说成保证物理连续布局。实际并没有这个普遍保证。[einops 官方说明](https://einops.rocks/api/rearrange/) 允许在可行时返回视图，[PyTorch 视图说明](https://docs.pytorch.org/docs/stable/tensor_view.html) 也明确区分视图与连续存储。

我用真实 CPU PyTorch 2.7.1 和 einops 0.8.1 执行了相同例子，而非只做 JS 自检：

| 操作 | shape | stride | 共享原存储 | 连续 |
|---|---|---|---|---|
| 原输入 | `[3,8]` | `[8,1]` | 是 | 是 |
| 拆轴 | `[3,2,4]` | `[8,4,1]` | 是 | 是 |
| 换轴 | `[2,3,4]` | `[4,8,1]` | 是 | 否 |
| 再调用 contiguous | `[2,3,4]` | `[12,4,1]` | 否 | 是 |

因此图必须把逻辑分组和存储分开画，否则视觉化只会把错误讲得更有说服力。原文留在出处折叠区，额外讲解标注了纠正，没有悄悄改成看不出来源的新课文。

### Softmax：只改一个分数，三个概率都会受影响

分数 `[1,2,3]` 得到约 `[0.0900,0.2447,0.6652]`。把第一个分数改成 3 后，概率变成约 `[0.4223,0.1554,0.4223]`。第二、第三个原始分数没有变，概率却变了，因为三项共用的分母变了。

图依次显示分数、减最大值后的指数值、归一化概率、修改后的概率；真实 PyTorch 核对了结果、和为 1、整体加 1000 后不变。没有拿归一化后每项独立变化的假动画解释共享分母。

抽帧曾发现三个“候选”标签只在最后一个状态出现。数值检查没有发现这个问题，实际画面发现了；修订时把标签的出生时间固定在初始状态。这个小问题很能说明为什么不能用测试通过代替读图。

### 计算与搬运：看瓶颈，不是假装测 GPU

假想机器每毫秒算 100 FLOPs、搬 10 Bytes。任务算 1000 FLOPs，计算时间是 10 毫秒；搬 1000 Bytes 要 100 毫秒。把数据搬运降到 100 Bytes、50 Bytes 后，搬运时间变成 10、5 毫秒；在计算和搬运充分重叠的简化假设下，总时间约为 100、10、10 毫秒。

这解释了为何提高 `FLOPs/Bytes` 可以先解决搬运瓶颈，后来却不能继续按同样比例加速。图把工作量和时间分成不同阶段，避免把 1000 FLOPs 和 1000 Bytes 画成两个实际耗时一样长的任务。[官方 Lecture 2 页面](https://cs336.stanford.edu/lectures/?trace=lecture_02) 也在讨论这类估算时明确采用重叠假设。

**这些速度是手选的教学参数，没有测这台电脑的 GPU，也没有训练任何权重。** 原型中直接写明了这个边界。

## 工程中最需要补齐的不是动画库

### 1. 先守住原文，再做漂亮排版

原 reader 在 CS336 的四册教材中遇到 5 处过大的公式区间。有的未闭合公式把后面上千行纳入解析，例如第一册第 876–2009 行，共 1134 行。它恢复出看似正常的标题，但章节原文切片使用了不对应原文的局部偏移；实际得到 4 个空章节、6 个非空却从错误位置开始的章节。

新导入器先用原始 Markdown 的结构确定章节起止，再在各自区间里处理公式。坏公式保留原文字样并降级显示。21 份文档逐字拼接回原文成功，128 章标题与原 reader 相同，新章节原文没有空切片。**这证明没有丢原文，不证明原文讲得对。**

当前独立导入器处理了 6 个过大的公式区间；KaTeX 还报告 2 处公式排版失败，都在第一篇笔记。这些问题保留并提示，未靠删除内容制造零错误。允许较长公式的界限仍是保守实现选择，今后需要逐处核对，而非自动把异常都修成猜测的数学。

### 2. 文字和图必须明确绑定

当前只有 12 段经过核对的讲解绑定 12 个状态。绑定记录有段落 ID、文字哈希、来源文件哈希、固定提交、状态和取样位置。修改讲解或原文会拒绝沿用旧映射；浏览器发现页面段落和配置不一致时，只停用那个段落，其余内容仍可读。

不要让浏览器每次鼠标移动都把整页发给 AI，再猜现在该播放什么。那会增加延迟、费用和不可重复性。AI 可以在编写阶段提出一份映射，作者核对并冻结后，阅读端只是执行。

整册插入也不靠“看起来差不多的标题”。第 1 册一个位置、第 4 册两个位置，都要求固定原文标题恰好匹配一次；有歧义就停止。其余章节保留普通阅读。现阶段没有自动把所有旧段落套上动画。

### 3. 失败之后教材还得能读

正文和静态图先存在 HTML 里，JS 只是增强。图延迟加载，共用一次 WASM 获取；离开页面或显式销毁后，尚在加载的图不会复活。已加载的三张图保留供回读，没有实现任意规模教材的缓存淘汰。输入调试记录有数量上限，仅在本页内存，不上传阅读轨迹。导入的 HTML、危险链接和自动外链图片有明确处理，公式不开放任意 HTML 权限。

离线打包本身也有真实失败：初次把打包结果当成单个对象、以及用 JS 替换字符串嵌入大段代码，导致输出语法错误。修正后重新执行了断网浏览器检查，早先失败文件与日志保留。不能只看到一个 HTML 文件已经生成就宣布离线可用。

### 4. 别把同一套代码的自检当成独立验证

本轮把数学检查、实际图像采样、输入控制、整册导入、离线打开分开。张量和概率额外用真实 PyTorch 核对；不同访问顺序下到达同一状态的图像做了像素一致性比较；最后看过实际桌面和手机画面。仍需真人核对教学解释和阅读体验。

手机画面采用浏览器的 390×844 尺寸与触屏属性模拟，持续测试用程序滚动定位。没有拿实际 Android／iPhone 测触摸手势、系统字体和耗电；桌面鼠标、滚轮、键盘输入则由浏览器测试工具实际触发。

30 分钟测试对应较早版本，原 JS 副本和哈希保留；后来的静态模式与图形排版修订不能借它冒充完整验证。首次长时间实际输入运行退出 143，未写出完整汇总；最后可见鼠标 570 秒、手机滚动 571 秒的记录都没有观测到错误，但这一轮不计通过。新版分段持久化结果，完整重跑另存自己的源码哈希。JS 堆取样约 4.0–5.3 MB，发生过回收，这不是整个浏览器的内存占用，也不足以证明任何长期泄漏都不存在。

最终三图各 600 次同步 seek 的测量，桌面张量图中位数约 0.2 毫秒、95% 位置约 0.3 毫秒，最慢约 10.2 毫秒；Softmax 有约 15.2 毫秒的最慢样本。它只计同步定位和绘图调用，**没有测屏幕实际呈现延迟、鼠标停留时间或 GPU 吞吐量**。有些结果显示 0，来自计时分辨率，不能理解为零成本。前轮 Softmax 最慢约 18.9 毫秒的结果同样保留；这几次不能构成性能提升对照。

另外，按照最小锁文件在全新目录实际运行了 `npm ci`、构建、21 份教材导入和离线打包。21 个普通 HTML 与实验页单文件逐字一致。两册单文件保留了导入耗时记录，所以字节不同；去除这段明确标识的可变元数据后内容一致。这是实际重建检查，不是只把依赖表写进 README。

## 现有研究能支持什么

把对应的文字和图放在一起，是有研究依据的设计选择。一项 51 名对该主题不熟悉的大学生的闪电形成实验发现，整合布局比拆开的布局表现更好；但主题和材料与 CS336 不同，不能直接推算我们的收益。[原研究](https://journal.psych.ac.cn/acps/EN/10.3724/SP.J.1041.2015.00224)

“动画一定比静态图好”则没有这种普遍保证。Mayer 等人的四个机制学习实验中，静态材料在部分记忆和应用比较中更好，其余没有显著差异；静态纸面与带旁白电脑动画也包含媒介差异，不能据此说所有连续动画没用。它提醒我们认真做完整静态对照。[原论文](https://adrenaline.ucsd.edu/kirsh/fileupload/illustrations%20vs%20animations.pdf)

鼠标也不是天然的视线替身。CHI 的网页搜索研究实际观察了 36 位参与者，发现停留、阅读、滚动和点击等行为不同；搜索任务的结果不能直接推广到学习，但足以提醒我们提供可退出的跟随方式。[微软研究页](https://www.microsoft.com/en-us/research/publication/user-see-user-point-gaze-and-cursor-alignment-in-web-search/)

此外，[Stanford CS336 官方课程](https://cs336.stanford.edu/) 的 [Lecture 2](https://cs336.stanford.edu/lectures/?trace=lecture_02) 已有讲解、代码、执行结果组合的 trace 页面。本轮实际打开核对过张量和算术强度内容。它是需要认真比较的基线；我们的改进候选在于长篇教材和读者的段落节奏，不应只与粗略视频相比。

## 旧项目该不该重构

旧仓库变得难理解是有原因的：本轮盘点受 Git 跟踪的文件时，`evaluation/` 有 2185 个，`tools/` 50 个，`runtime/` 4 个。这些实验记录不是都该删掉的垃圾；保留失败和出处本身有价值。但日常入口与大量历史实验混在同一个目录体系里，读者容易把“已有工具”误解为“已经证明有效”。

还有两处具体问题值得修：

1. [batch 初始化](/home/yang-zhi/文档/ChatGPT/concept2motion/tools/batch.py:222) 拷贝隔离运行快照时遗漏了 `capture_frame.mjs`，而渲染入口会导入它。此前实际控制得到 `ERR_MODULE_NOT_FOUND`；本轮又核对了当前拷贝清单。正常主目录运行不能覆盖这种隔离入口问题。
2. [review 校验](/home/yang-zhi/文档/ChatGPT/concept2motion/tools/review_run.py) 只检查证据路径等元数据。本轮对当前函数做了明确标记的合成反例：文件内容根本不是 JPEG、视频缺失，仍能通过。它不能承担“确实有可观看渲染证据”的保证，需要真实解码／完整产物检查。

我也核对了容易误判的一点：当前 `feedback_cycle.py` 已经合并全视频检查的 findings；不能把早先另一条增强反馈路径的遗漏，直接说成当前这个函数仍有同样错误。旧 [VideoScore 负结果](/home/yang-zhi/文档/ChatGPT/concept2motion/evaluation/2026-10-07/videoscore-validation-v2/REPORT.md) 仍应保留，不应因为新教材方向有希望就改写评分器结论。

如果继续旧视频研究，先修上述证据入口，再把当前主路径与历史实验分清，不必为了“代码漂亮”一次性大改。若目标是你这次说的阅读教材，**不建议先重构旧整个平台**：这版已经证明新的阅读端不需要依赖它。

可以借的部分有三个：按确定状态取样；保存原文、输入和版本；把数值检查与实际画面审阅分开。旧特定场景运行时、自动裁判分数、作者批量流程没有强行搬进来。这次没有修旧文件或删除旧历史，也没有凭沉没成本选旧架构。

## 下一步怎么做才不容易走偏

### 先做一章，限制图的数量

选一章你正在学、已经有可靠逐字稿的内容。挑 6–10 个“没图就容易误解”的地方，比如换轴、共享分母、反向传播数据流、KV cache 或分块内存访问。每个图写清楚变量是什么、哪一段触发哪一态、什么保持不变；术语定义和铺垫段落不必全部动起来。

先请熟悉课程的人核对讲解和图，再请读者试读。尤其警惕教材生成时的错误被可视化放大。本轮发现的连续存储误述说明，Video2Book 的详细输出也不能代替原课核查。

### 认真比较，不先问“好不好看”

可以先找约 12 位同学做找问题的小试验；这个人数不能支持普遍学习效率结论。安排三个相近难度的小主题、三种方式：普通文字、完整静态图、段落跟随图。让不同人以不同顺序、不同主题使用这些方式，避免所有人先看文字版再看已经熟悉的动态图。

记录前测、读完能否不看图解释、换一个数字或情境能否应用、回读次数、误切、暂停次数和主观分心程度。不要只看用时：读得快可能只是跳过了。也不要拿完全相同的问题反复考。

当前静态模式已经显示全部四态，避免拿一张冻结初始图当完整静态教材。但静态 SVG 和 Canvas 的布局仍不同，正式比较应改成同版状态截图，统一文字、字号、布局和信息量；否则差异可能来自排版。测试的目的应是发现“什么时候图有用、什么时候跟随碍事”，不是想办法得到一个漂亮的总分。

### 最后再扩大自动生成

一章读起来有用，再连接真正的听音和作者流程。生成阶段应输出正文、图所用的数据、每段状态映射和出处；构建阶段做数学与图像检查，阅读端执行冻结结果。需要改来源或表达时重新核对，不在阅读时临时猜。

Zanim 可以继续用：任意顺序 seek 已经实际可行。若以后要跨浏览器和 Python/native 使用同一份图，当前浏览器 Text 对象不能直接导出 Scene IR，需要选择可移植文字／公式资源并重新验证；这不是本轮 HTML 阅读的阻塞，不必提前把整个跨后端平台做完。

最后还有一个发布边界：[courses 仓库说明](https://github.com/LINJIANG12/video2book-courses#版权与免责声明) 限定个人学习、禁止商业用途和作为原课替代品传播，文本没有开源许可证。当前全文输出留在本机忽略目录。将框架公开和将课程全文公开是不同决定；要做公开产品，需要另找允许发布的课程材料或取得许可。这是实际素材约束，不能因为生成成 HTML 就忽略。

## 最终建议

把这个方向继续推进成“能认真读的一章”，我支持。优先验证正文与图的对应关系、回读和完整静态对照，把光标作为可选择的控制方式。当前已有可运行产物、整册导入和具体反例；学习收益、批量图解生成成功率、全课内容正确性仍未得到证明。

这轮没有需要你批准的部署动作：未推送、未公开课程、未增加账号或长期服务。最终结果与候选记录见 `RESULTS.json`、`candidates.json`，重建入口见源码 README，失败日志和全部截图在本机忽略目录中保留。
