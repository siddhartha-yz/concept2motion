## 两幅图的取舍

1. **计时停了，计算还在继续**（queued-clock，紧接 async-computation-009，覆盖至 010）。原文说明异步返回，但计时边界和实际完成边界没有直接对照。图中蓝色表示提交，橙色表示 GPU 计算，淡色表示尚未执行的既定工作；编号对应同一任务。提交在 1.2 结束，计算在 6.4 结束。时间游标与已执行部分按连续 0–1 进度变化，任务完成数只在真实完成边界更新。默认静止于 0，使用共享运行时拖动、单步或主动播放，不注册计时器或滚动推进。
2. **重叠能省多少，取决于较慢的一段**（pipeline-bottleneck，紧接并仅覆盖 021）。原文给出总时间公式，却没有展示提交成为瓶颈的情况。用同一时间尺对照同步执行和异步流水线，改变每次提交时间 t₁，实际重算每个任务的就绪、开始、完成时刻。采用 interaction=parameters，避免给完整排程添加无意义的播放运动。细连接线只表示“提交完成 → 可开始计算”的约束；GPU 同行保持顺序执行。

没有再画前后端架构或计算图依赖，原书已有三幅相关原图。没有把原文段落重复写进图，没有说明墙或装饰卡片。桌面绘图区分别为 320、390 px，手机为 330、390 px。固定横轴避免参数变化被自动缩放掩盖；稳定图元 id 保持任务身份。

## 数学核对与解释边界

全部时间为手选示例单位，不是 CPU/GPU 实测、训练结果或框架性能结论。图一假设初始空队列、单 GPU 顺序执行，每次提交 0.4、计算 2，不计同步调用的额外开销。真实排程为提交 [0,0.4]、[0.4,0.8]、[0.8,1.2]，计算 [0.4,2.4]、[2.4,4.4]、[4.4,6.4]。例如 t=3.5 时已提交 3 个、完成 1 个。

图二采用单提交线程、单计算线程、4 个独立任务。每次计算 t₂=2，返回 t₃=0.5；同步每次返回，异步仅最后返回。异步按 `开始_i = max(提交完成_i, 上一计算完成)` 排程。该模型的精确总时间为 `t₁ + t₂ + (N−1) max(t₁,t₂) + t₃`。t₁≤t₂ 时才能简化为原文的 `t₁ + N t₂ + t₃`；t₁>t₂ 时 GPU 有空档。原文给出的 `N t₂ > (N−1)t₁` 总量条件本身不足以保证每一步连续供给，此处保留原文，图中明确区分“计算较慢”和“提交较慢”。例如 N=4、t₁=2.1 满足该总量条件，但排程耗时为 10.9，简化式为 10.6。
