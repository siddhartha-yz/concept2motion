# 待解决：评价怎样驱动下一次修改

状态：**未解决，已记录；本次不启动新的生成或修订实验。**

记录日期：2026-10-03。

## 用户指出的问题

评价两个视频的优劣之后，系统没有完整地把评价转成改进。用户希望有类似“反向传播”的过程：从结果上的问题追溯到创作决定，修改后再验证，而不是不断产出评分报告。

## 当前缺口

最新对照的流程是初稿 → 普通自查或程序检查 → 一次修订 → 强模型最终比较。最终比较故意不参与作者修订，以保持实验测量独立；这不代表产品已经形成自动改进闭环。

仓库已有局部补丁、版本保存、程序反馈和常驻预览，也做过有限视觉修订。但缺少统一的“问题证据 → 原因假设 → 修改票据 → 修改后验证 → 保留或回退”流程。最终画面裁判的意见还没有自动接入这条流程。

## 要实现的行为

```text
生成 → 评价 → 定位问题 → 提出修改假设 → 局部修改 → 复评
                         ↑                          ↓
                         └──── 保留改进或回退 ──────┘
```

每张修改票据至少记录：

- 发生在哪个时刻、哪个对象，具体画面证据是什么。
- 哪个创作决定可能造成问题；这是待验证的假设，不是裁判已经证明的原因。
- 基于哪个源码版本，允许修改哪些对象、时间段或文件；哪些内容需要保持。
- 修改后预期改善哪一项，如何验证，以及共享预算和停止条件。
- 实际修改、重新渲染、目标问题是否改善、是否引入其他退化、保留或回退的理由。

例如：指数条已经变长，但标签仍只显示原始分数 → 假设对象对应关系丢失 → 延长指数标签的可见时间 → 检验能否辨认对应关系，同时检查遮挡、数值与其他阶段是否变化。

这里更新的是分镜、对象、时序和代码，没有更新模型权重，不称作实际梯度反向传播。先做当前作品的局部循环；跨作品经验积累另有假设，尚未实现或证明。

## 解决这个问题需要交付什么

1. 把实际画面问题转成结构化修改票据，保留证据和原因假设，避免只有“更清楚一点”或长篇自我反思。
2. 在新版本上执行有边界的修改，保存前后源码、画面、检查和耗时。
3. 针对修改目标复查，同时检查保护区域和其他评价方面；假设失败则保留失败并回退。
4. 分开用于指导修改的评审与用于最终比较的评测，后者不参与修订。独立上下文不意味着两个评审的模型偏差完全独立。
5. 在同模型、同任务和预先固定的总预算下，比较普通自查与上述循环；反馈、修改、复评和失败都计入成本。
6. 用未用于调试循环的任务检验效果。先证明有用，再扩展经验库或代理平台。

评分标准的选择仍受[第一个待解决问题](evaluation-score.md)约束。本文件登记的是设计要求，不宣称这条闭环已实现或带来质量提升。
